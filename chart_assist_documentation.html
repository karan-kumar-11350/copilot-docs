Feature Overview — DX Suggestion
Automatically suggests ICD-10 codes from encounter notes using MetaMap NLP
Chart Assist (DX Suggestion) reads physician encounter notes, runs them through MetaMap Lite NLP, and converts identified medical concepts into ICD-10 diagnosis codes that the doctor can accept with one click.

What it does

  1. Extracts text from note sections: Assessment Notes, Chief Complaints, HPI, Physical Exam, Subjective Notes
  2. Runs text through MetaMap Lite (NIH/NLM local NLP library) to extract CUIs
  3. Maps CUIs → SNOMED CT codes → ICD-10 codes
  4. Presents suggestions as checkboxes; doctor clicks to add to the encounter

Key Technologies

TechnologyRole
MetaMap LiteLocal Java NLP library from NIH/NLM for biomedical text processing. No external API calls.
UMLS MetathesaurusUnified Medical Language System — concept database backing MetaMap
SNOMED CTClinical terminology standard — intermediate mapping layer
ICD-10International Classification of Diseases — final output codes for diagnosis

Simplified Pipeline

1
Doctor writes notes — Assessment, Chief Complaints, HPI, PE, Subjective
2
Clean text — Strip HTML, remove non-ASCII, replace medical abbreviations (pt→patient, hx→history)
3
MetaMap NLP — Sentence detection → Tokenization → POS tagging → Chunking → UMLS concept identification → CUI extraction
4
CUI → SNOMED — Lookup in cuiSnomedMap.bin
5
SNOMED → ICD-10 — Rule evaluation in icd10SnomedMap.bin (gender, age, laterality rules)
6
ICD-10 → Diagnosis ID — Lookup in DIAGNOSISLIST table
7
Deduplicate & rank — Merge across note types, promote codes appearing 3+ times

MetaMap NLP Engine
7-step NLP pipeline: abbreviation expansion → CUI extraction with negation detection
MetaMap Lite is a local Java library from NIH/NLM. It maps biomedical text to concepts in the UMLS Metathesaurus. No external API calls — all processing is in-process on the MetaMap server.
flowchart TD INPUT["Input: Doctor Notes\ne.g. Patient has persistent cough and mild fever"] A1["Step 1: Abbreviation Replacement\npt to patient, hx to history\nTrieWordSearcher with notesAbbreviations.properties"] A2["Step 2: Sentence Detection\nOpenNLP en-sent.bin"] A3["Step 3: Tokenization\nOpenNLP en-token.bin"] A4["Step 4: POS Tagging\nOpenNLP en-pos-maxent.bin"] A5["Step 5: Chunking\nOpenNLP en-chunker.bin\npersistent cough to NP noun phrase"] A6["Step 6: UMLS Concept Identification\npersistent cough to CUI: C0010200\nmild fever to CUI: C0015967"] A7["Step 7: Negation Detection\nno fever to negated to SKIP\npersistent cough to NOT negated to KEEP"] OUT["Output: JSON Array\n[{cui: C0010200, cui_desc: Cough}, {cui: C0015967, cui_desc: Fever}]"] INPUT --> A1 --> A2 --> A3 --> A4 --> A5 --> A6 --> A7 --> OUT

Notes TextNegated?Action

MetaMap Processing Steps Inside getMappingForNotes()

  1. Replace medical abbreviations using TrieWordSearcher.replaceString()
  2. Create BioCDocument from text via FreeText.instantiateBioCDocument()
  3. Run MetaMapLite.processDocumentList():
    • Sentence detection (OpenNLP model)
    • Tokenization (OpenNLP model)
    • POS tagging (OpenNLP model)
    • Chunking (OpenNLP model)
    • UMLS concept identification against index files
  4. Iterate through detected entities
  5. Filter negated entities — entity.isNegated() = true → skip
  6. Extract CUI and description for each non-negated entity
  7. Return JSONArray of {cui: "C0015967", cui_desc: "Fever"}
Memory Warning: MetaMapLite loads the entire UMLS index (hundreds of MBs) into the JVM heap per instance. The singleton pattern in MetaMapImpl.java is not synchronized, which causes multiple instances under concurrent load. See Section 17 — Memory Issues.

Why Order Matters

  1. Priority: Suggestions from earlier note types appear first in the display
  2. Deduplication: The same DX code appearing across multiple note types gets a higher duplication_count and is promoted to the top if it appears more than 2 times
  3. Relevance: Assessment Notes contain the most medically precise language, so parsing them first yields the best initial results

Known Memory Issues — MetaMap JVM Overload
MetaMapLite architectural constraints that cause high JVM heap consumption under load
Context: MetaMapLite is an NLP library from the NIH National Library of Medicine. Its memory characteristics are inherent to its design and are not configurable. Understanding these constraints is important when planning server sizing and concurrency limits for the MetaMap server.
#Architectural CharacteristicMemory Impact
1Each MetaMapImpl instance loads the entire UMLS concept index into JVM heap on initializationHundreds of MBs per instance — the UMLS dictionary is large by design; MetaMapLite makes no attempt to lazy-load or page it
2processDocumentList() is not thread-safeConcurrent NLP calls cannot share a single instance; each concurrent thread requires its own isolated instance, multiplying the base heap cost
Scaling Implication: Because each MetaMapImpl instance independently loads the full UMLS index and processDocumentList() is not thread-safe, the memory footprint scales linearly with the number of concurrent NLP requests. Under high physician load this can cause sustained GC pressure, heap exhaustion, and MetaMap server OutOfMemoryErrors. The MetaMap server is therefore kept on a separate JVM (see Two-Server Architecture) to isolate these constraints from the main Charm EHR server.

Feature Overview — Plan Suggestion
KNN + Jaccard Distance ML recommends Rx, Labs, Images, and Notes from similar encounters
Plan Suggestion uses K-Nearest Neighbors ML to recommend treatment plans based on a patient's current DX codes. It finds the most similar historical consultations in the practice and suggests what was prescribed/ordered for those encounters.

What it recommends

  • Prescriptions (Rx) — with drug allergy safety checks via LEXI API
  • Lab Orders — with specific test names
  • Image Orders — X-ray, MRI, CT, etc.
  • Treatment Notes — physician notes from similar encounters
  • Patient Notes / Instructions — patient-facing instructions
  • Diet Notes — dietary recommendations
  • Lifestyle Notes — lifestyle modification suggestions

3-Phase ML Pipeline

1
Data Migration — Flatten historical consultations into AIDXDERIVATIVES table. Assign numeric indices to DX codes in DXCONDITIONINDEXER.
2
Model Training — Generate SVM sparse vectors from migrated data. Upload to ZLabs KNN API with distanceMetric=JACCARD_DISTANCE. Store model ID in AITRAINEDMODELDETAILS.
3
Prediction — Build query vector from current encounter's DX codes. Query ZLabs KNN model (top 30 neighbors). Filter by 80% match threshold. Assemble plan data with drug allergy checks.

Key Concepts — KNN with Jaccard Distance
Jaccard Distance = 1 − (|A ∩ B| / |A ∪ B|). Match% = (1 − distance) × 100

Jaccard Distance Example

FieldValue
Query DX codes{J06.9, R05, J02.9}
Historical consultation DX codes{J06.9, R05, R50.9}
Intersection |A ∩ B|{J06.9, R05} → size = 2
Union |A ∪ B|{J06.9, R05, J02.9, R50.9} → size = 4
Jaccard Distance1 − (2/4) = 0.5
Match Percentage(1 − 0.5) × 100 = 50%

Why KNN with Jaccard Distance?

  • Sparse binary data: DX codes are naturally represented as binary presence/absence vectors
  • Set similarity: Jaccard measures set overlap — exactly what's needed for "how similar are two DX profiles?"
  • Interpretable: The distance directly translates to a match percentage doctors can understand
  • No training bias: KNN is instance-based, adapts immediately when new data is migrated
  • Simple to retrain: Just re-upload the dataset; no complex model tuning needed

Optimization & Ranking Algorithm
optimisePlanRecommnendation() — frequency count + date boost + deduplication
All plan items (Rx, labs, images, notes) pass through the same ranking pipeline. Items appearing more frequently across matched consultations rank higher. More recent consultations receive a date boost.

Ranking Logic

flowchart TD INPUT["Plan items from AIDXDERIVATIVES\n(Rx, Labs, Images, Notes)"] COUNT["Count frequency of each item\nacross all matched consultations"] DATE["Apply date boost\nMore recent consultation = higher weight"] SORT["Sort descending by\n(frequency * date_weight)"] DEDUP["Deduplicate items\nKeep highest-ranked copy per item"] ALLERGY["Drug allergy flag injection\nSevere / Moderate / Mild / None"] OUTPUT["Final ranked plan\nplanResponse()"] INPUT --> COUNT --> DATE --> SORT --> DEDUP --> ALLERGY --> OUTPUT

Score Computation

FactorDescription
Frequency countNumber of matched consultations containing this item. Higher = more common treatment for these DX codes.
Date boostMore recent consultations contribute a multiplier. Ensures newer clinical patterns rank above older ones.
DeduplicationSame drug / lab / image deduplicated by key (drug name + strength for Rx, test name for labs/images). Highest-ranked copy kept.
Allergy flagInjected after ranking. Does NOT affect rank order — doctor sees the item regardless (with warning badge).
